## Часть 2: Проверка и критерии приемки пет-проектов

---

### 🎟️ Проект 1: High-Load Booking & Auction Engine

#### Бэкенд (Go):
- [ ] **Архитектура:** Структура проекта оформлена по Clean Architecture / Standard Go Project Layout. Бизнес-логика не зависит от Gin/Chi или Postgres.
- [ ] **Защита от овербукинга билетов:**
  - Реализован механизм удержания места (Seat Hold) на 10 минут через распределенную блокировку в Redis.
  - Покупка места выполняется внутри строгой транзакции PostgreSQL с проверкой статуса.
  - Написан тест на конкурентность (100 одновременных запросов на покупку одного и того же места — ровно 1 успешный заказ, 99 отказов).
- [ ] **Аукцион в Real-Time:**
  - Подключение по WebSocket, аутентификация через JWT при установке соединения.
  - При повышении ставки событие мгновенно транслируется всем активным зрителям лота.
- [ ] **Transactional Outbox + Kafka/RabbitMQ:**
  - При успешном завершении аукциона/оплате билета создается запись в таблице `outbox`.
  - Фоновый воркер читает непосланные сообщения и отправляет их в брокер.
- [ ] **Тестирование и метрики:**
  - Интеграционные тесты с базой данных написаны с использованием **Testcontainers-go**.
  - Сервис отдает метрики в формате Prometheus на эндпоинте `/metrics`.
  - Проведено нагрузочное тестирование через **k6** (сценарий симуляции 500+ виртуальных пользователей).

#### Фронтенд (React 19 + TypeScript):
- [ ] Использован строгий TypeScript (без `any`), все DTO и события WebSocket строго типизированы.
- [ ] Интерактивная карта зала/мест (Seat Map) с цветовой индикацией: Свободно / Забронировано / Заблокировано мной.
- [ ] Динамический таймер аукциона с автоматическим продлением при ставке на последних секундах.
- [ ] Подключение WebSocket автоматически восстанавливается с экспоненциальной задержкой (Exponential Backoff) при обрыве сети.

### 🎮 Проект 2: Real-Time Multiplayer Game Server

#### Бэкенд игрового сервера (Go):
- [ ] **Авторитетный сервер (Authoritative Server):**
  - Вся игровая физика (координаты, коллизии, попадания, здоровье) рассчитывается исключительно на сервере. Клиент не может «нарисовать» себе победу.
- [ ] **Изолированный Game Loop:**
  - Каждая активная сессия/матч работает в своей горутине с фиксированным тикрейтом (например, 30 или 60 тиков в секунду с использованием `time.NewTicker`).
  - Сервер собирает пользовательские инпуты за тик, производит расчет и формирует дельту состояния.
- [ ] **Оптимизация протокола:**
  - Игровые пакеты сериализуются через **Protocol Buffers** поверх WebSocket.
- [ ] **Система лобби и матчмейкинг:**
  - Игроки добавляются в очередь поиска матча.
  - Сервис матчмейкинга на базе Redis Sorted Sets подбирает соперников с близким рейтингом MMR/ELO.
- [ ] **Таблица лидеров (Leaderboard):**
  - Эндпоинт получения топ-100 игроков, работающий мгновенно за $O(\log N + M)$ за счет команды Redis `ZREVRANGE`.

#### Фронтенд игры (React 19 + TS + Canvas / Pixi.js):
- [ ] Компонент рендеринга игры на HTML5 Canvas или Pixi.js.
- [ ] Реализована плавная **клиентская интерполяция** (Interpolation/Lerp) координат между серверными тиками, чтобы движение персонажей не дергалось.
- [ ] Экран лобби со списком активных комнат, кнопкой «Поиск матча» и поиском по лидерборду.
- [ ] Отображение пинга до сервера в реальном времени.
